# Platypus 2.13 · Storage

Development plan, one task at a time. It goes in the repository as `docs/plans/2.13-storage.md`, branch `dev-2.13-storage`.

Checkboxes:
- `[ ]` to do;
- `[~]` in progress;
- `[x]` done;
- `[!]` blocked, with the reason underneath.

At the bottom there is the **Journal**: every step adds an entry to it.

This plan replaces part E of `docs/plans/2.11-3.0-feedback-storage-server.md` (the old "2.12 storage"). Part F (server mode) stays there and becomes 3.0.

## The idea in one line

Today Platypus keeps a few JSON files and rebuilds everything else from the transcripts. That is enough for the office, but not for questions about months of history:

- "Does this project go round in circles more than before?"
- "Since the feedback has been on, are there fewer claims without evidence?"

2.13 gives the engine a single document store, with these properties:

- **Backend:** SQLite built into Node on the desktop; the same interface will run on MongoDB in 3.0.
- **History:** months of history are kept.
- **Measurement:** the feedback to agents can be measured with a real control group.
- **Privacy:** only derived facts, never the text.

## How to work (the loop reads this every iteration)

The state of the work is in the checkboxes, in the Journal and in `git log`, not in your memory. Re-read them every time.

**1. Orient yourself.**
- Check that you are on branch `dev-2.13-storage`.
- If the tree is dirty, an iteration was interrupted:
  - find the `[~]` task and the last Journal entry;
  - finish the work, or `git stash` it if it is confused;
  - note the choice in the Journal.

**2. Prepare.**
- Take the **first** `[ ]` task, in the order written, and mark it `[~]`.
- Read its description, the code it points to and the Journal entries of the tasks it depends on.
- Split a big task into sub-steps listed in the Journal, one commit each ("S3 (1/3): …").

**3. Implement.** Follow the rules below.

**4. Verify.**
- Always:
  - `npm test` must end with "Tutto a posto.";
  - `npm run i18n:check` must report nothing missing.
- Run the store conformance suite and the benchmark when the task touches the store.
- UI changes: take a screenshot with `PLATYPUS_SNAPSHOT` and look at it.
- If the same problem fails three times, mark the task `[!]` with the reason and move on, unless the next task depends on it.

**5. Close.**
- Mark the task `[x]` or `[!]`.
- Add a Journal entry: date, task, what was done, how it was verified (commands and results), decisions, doubts for Max.
- One commit per task: an English imperative message with the task id, plus your usual attribution lines.

**6. Continue or stop.**
- Go on to the next task; with `/loop`, use the minimum delay.
- Every five closed tasks, write Max three lines: done, blocked, next.
- **Stop and write to Max, in Italian and briefly, when:**
  - the plan is finished;
  - you need his permission: touching his real `~/.platypus`, installing software, pushing;
  - a product decision is not settled here;
  - `npm test` cannot be made green again.

## Project rules for this plan

- **No npm dependencies in the engine.** `node:sqlite` is part of Node; MongoDB (3.0) will live in a separate package.
- **Isolation:** every command that starts the engine uses `PLATYPUS_PORT=47870` and `PLATYPUS_DATA_DIR=<worktree>/.platypus-dev`. Never touch Max's real `~/.platypus` without asking, except in S15, which says how.
- **Privacy by construction:**
  - the store accepts only the fields declared for each collection (S6);
  - never prompt text, replies, tool output, file contents, credentials or e-mail addresses;
  - paths are relative to the project root.
- **Behaviour does not change** for someone who does not look at the history: the office, the map, the Book and the 2.11 feedback work exactly as before (tests prove it).
- **Never block the office:**
  - writes are batched (at most every 2 s, in one transaction);
  - heavy queries do not run in the SSE path;
  - if the database cannot be opened, Platypus keeps working without history and says so.
- **Texts:**
  - `tr()`/`trn()`, never `t()`;
  - English translations in `src/i18n/locales/en/store.json`.
- **Never:**
  - `git push`, merge into main, or rewriting commits already made;
  - `npm run hooks:install`;
  - Max's real data in the repository;
  - the @decisyon.com address as commit author.

## S2 · The `store` interface, the memory backend and the conformance suite  [x]

- `src/core/store/index.js`: `openStore({backend, dir}) → store`.
- **Collection API** (`store.collection(name)`):
  - `get(id)`, `put(doc)`, `patch(id, partial)`, `delete(id)`;
  - `find(filter, {sort, limit, skip, fields})`, `count(filter)`, `deleteMany(filter)`;
  - `append(doc)`, for logs.
- **Store API:**
  - `store.transaction(fn)`;
  - `store.declare(name, {fields, indexes, retention})`;
  - `store.forgetProject(key)`;
  - `store.export(name, dir)` and `store.import(name, file)`;
  - `store.info()`;
  - `store.close()`.
- **Filter language:** a documented subset of MongoDB's, so that 3.0 does not have to rewrite anything:
  - equality, `$in`, `$gt`/`$gte`/`$lt`/`$lte`, `$exists`, `$or`;
  - dotted paths;
  - sort on one or more fields.
  - Nothing else: an unsupported operator throws an error, it is not ignored.
- **Data conventions that work on both:**
  - `_id` as a string (ULID, sortable by time);
  - times as milliseconds (numbers);
  - no field names with `.` or `$`.
- **`memory` backend:** used by the tests, by the demo and as an emergency fallback (S4).
- **Conformance suite:** `scripts/store-conformance.js`, one suite for every backend.
  - It is chosen with `PLATYPUS_STORE_BACKEND` and is part of `npm test` for `memory`, and for `sqlite` from S3.
  - It must be ready to run unchanged against MongoDB in 3.0.

## S3 · SQLite backend  [x]

- **File:** `src/core/store/sqlite.js` with `DatabaseSync`, file `dataDir()/platypus.db`.
- **Tables:** one per collection, with `_id TEXT PRIMARY KEY`, `project TEXT`, `t INTEGER` and `doc TEXT` (JSON).
  - Indexes on the fields declared in `declare()`, as expression indexes on `json_extract`.
  - The filter is translated into SQL with parameters only, never strings concatenated with values.
- **Pragmas:**
  - `journal_mode=WAL`;
  - `synchronous=NORMAL`;
  - `busy_timeout=3000`;
  - `foreign_keys=ON`.
- **Write queue:** in-process, flushed in a single transaction at most every 2 s, or when 500 documents are reached; flushed on close.
- **Done when:** the conformance suite passes on `sqlite`.
- **Benchmark:** `scripts/store-bench.js` with synthetic data, measuring:
  - ingest of 1000 steps per second;
  - `find` by project over the last 30 days on 1,000,000 steps, under 50 ms;
  - DB size per million steps.
- Put the results in the Journal and in `docs/plans/storage-measurements.md`.

## S4 · Schema version, backups and failure  [x]

- **Schema version:** a `meta` table with `schemaVersion`; numbered migrations in `src/core/store/migrations.js`, run in a transaction at start-up (`BEGIN IMMEDIATE`, so two processes do not migrate together).
- **Backup:** before every migration, a copy with `VACUUM INTO 'platypus.db.bak-<version>'`. Keep the last two.
- **At start-up:**
  - run `PRAGMA quick_check`;
  - if the DB is corrupt or cannot be opened, rename it to `platypus.db.broken-<date>` and fall back to the `memory` backend;
  - the office shows a banner: "history not available: <reason>".
  - Nothing crashes.
- **Tests:**
  - a fake migration;
  - a file corrupted on purpose;
  - a read-only folder.

## S5 · Project key  [x]

3.0 will share one Book per repository across several machines, so the key has to be ready now.

- **The key:**
  - `projectKey` = sha1 of the normalised `git remote get-url origin`:
    - lower case for the host;
    - no `.git`;
    - ssh and https made equal;
    - **any credentials removed** (`user:token@`);
  - if there is no remote, the sha1 of the absolute path.
- **Aliases:** the `projects` collection keeps them, so the old keys of the Book (sha1 of the path) stay recognised.
  - Store the remote **without credentials**, and the folder name only.
- **Laziness:** read git once per project with a cache; never in the event path.
- **Tests:**
  - URLs with a token, ssh, https and Windows paths all give the expected keys;
  - no credentials ever end up in the store.

## S6 · Privacy guard  [x]

- **Declared fields only:** every collection declares its allowed fields and their types. `put`/`append` reject (in development) or drop (in production) every field that is not declared, and log it once.
- **Paths:** relative to the project root. Absolute paths outside the project become a hash with the file name alone.
- **One-line excerpts** (only where 2.11 or 2.9 already show them, and only on request): pass through a filter for tokens, keys, passwords, connection strings (from the old E4), e-mail addresses and IBANs before being saved. Reuse it if a filter already exists.
- **Test:** a document full of forbidden fields and secrets goes into the store; reading the raw DB file, none of those strings appears.

## S7 · Collections  [x]

Declare them with fields, indexes and retention:

| Collection | Content | Default retention |
|---|---|---|
| `projects` | key, aliases, remote without credentials, folder name, first/last seen | forever (until "forget") |
| `lessons` | the Book's lessons (kind, weight, evidence as references to steps) | weight below the threshold and older than 180 days |
| `steps` | metadata of each action: t, project, session, agent, action, tool, relative target, outcome, normalised error signature, phase. **Never text.** | 90 days |
| `sessions` | session summary: start/end, model, effort, counts of actions/errors/surprises/claims, cost | 365 days |
| `feedback` | 2.11 messages: function, mode (shadow/on), trigger, outcome after N actions | 365 days |
| `experiments` | the group assigned to each session for each feedback function | like `feedback` |
| `daily` | daily statistics (today's `stats.json`) | forever (small) |

Retention can be configured from the options, per collection.

## S9 · Switching the engine to the store  [x]

- `stats.js`, `bottega.js` and the 2.11 feedback read and write through the store.
- The steps are fed from `worldEnd`, through the queue.
- **Same behaviour as before:**

- **Opening the store must not delay the office** (from S4): the start-up check takes 600 ms on a 355 MB database, so the HTTP server starts first and the store is opened right after.

## S10 · Retention, size, forgetting, export  [x]

- **Retention:** at start-up and every 6 h, deleting in small batches so nothing blocks.
- **Retention, two special cases** (from S7): `lessons` are deleted only when their weight is under the threshold and they are not pinned (`retention.onlyIf: 'low-weight'`); in `daily`, the `last:<session>` documents are working state and go after 10 days, as `stats.js` does today.
- **Soft size limit:** 200 MB, configurable. Beyond it, the oldest `steps` go first, and the options say so.
- **"Compact":** `VACUUM`, from the options.
- **"Forget this project":**
  - from the Book and from the options, with a confirmation;
  - deletes every document of the project key (and its aliases) in every collection, then runs `VACUUM`;
  - `daily` has no project key: its documents keep the project by **name** (`projects.<name>`, `releases[].project`, `last.name`), as the report shows it. Forgetting must remove those entries too (from S7);
  - **test:** after forgetting, the raw DB file contains neither the key nor the path nor the folder name.
- **"Export":** one JSONL file per collection into a folder chosen by the user, or `~/Downloads/platypus-export-<date>/`.
- **UI:** a "Storage" section in OPZ with backend, size, retention per collection, compact, export, and the banner from S4 if needed.

## S11 · Experiment mode for the feedback  [x]

- **A fourth mode** for each 2.11 feedback function: `experiment`.
  - Each new session is assigned to `shadow` or `on`, 50/50, deterministically from the hash of the session id.
  - The assignment is saved in `experiments`.
- **Outcomes per group,** in a "Feedback" tab of the Book: for example "after an 'unstable command' message, how often does the agent re-run before investigating", or "how many claims without evidence per session".
  - Difference between the groups with a 95% interval.
  - With few cases, write "not enough data (n = …)"; never a verdict without numbers.
- **Explanation:** the UI says in one sentence why it is done this way. A before/after comparison would mix in model changes; random assignment does not.
- **Default:** off. Max turns it on for each function.

## S12 · History  [x]

- **API:** `GET /api/history?project&metric&from&to&bucket=day|week`.
- **Metrics:**
  - loops, stuck phases, surprises;
  - unstable commands (from the old E5, "flaky commands");
  - claims without evidence, stale memories;
  - lessons applied, feedback by group;
  - cost.
- **Book, new "History" tab:**
  - weekly lines per project;
  - one sentence of reading, for example "loops: fewer than a month ago".
  - Always with the number of sessions behind it, and "not enough data" when there are few.
- **Daily report:** one line of trend for the week.
- **Performance:** queries over 6 months of the benchmark data under 200 ms; if needed, materialised weekly aggregates in `daily`.
- **Session counts still to fill** (from S9): the `sessions` documents written today have times, model, effort, agents, actions, errors, cost and tokens. `surprises`, `claims`, `loops`, `stale` and `lessons` are declared but not computed yet: they need the surprise and grounding modules, which are too heavy to run every minute. This task decides how (at the end of a session, or from the stored steps).

## S12b · Archive search on the stored steps  [x]

Added by S0 from the old E5: it was the only feature of part E missing from this plan.

- **API:** `GET /api/history/search?project&file&command&error&from&to&limit`, answered from `steps` alone, without replaying transcripts.
- **What can be searched:** only what S7 already stores: the relative target, the tool, the outcome, the normalised error signature. For commands, the command core (`cmdCore`), passed through the S6 filter; never the full command line, never output.
- **UI:** a search field in the Book's "History" tab; each result opens its session in the archive.
- **Performance:** under 200 ms on the benchmark data, with the indexes declared in S7; never in the SSE path.
- **Tests:** search by file, by command and by error on synthetic steps; a query for a secret put in a command finds nothing in the raw DB file.

### 2026-11-19 · S5 Project key

- Done, in `src/core/store/project-key.js`:

### 2026-11-19 · S6 Privacy guard

- Done, in `src/core/store/privacy.js` and wired into `Store` (so it holds for every backend):
  - **Declared fields only.** `declare(name, { fields })` takes a type for each field: `string` (one line, at most 300 characters), `id`, `number`, `boolean`, `path`, `excerpt`, a nested object `{ a: type }`, an object with any keys `{ '*': type }`, or a list `[type]`. `_id`, `project` and `t` are always there. `put`, `append`, `patch` and `import` all pass through the guard.
  - **Two modes.** `guard: 'reject'` throws `StoreError` `undeclared-field` for a field that is not declared or has the wrong type; `guard: 'drop'` leaves it out and reports it once per field, with the name and never the value. The default is `drop`; it is `reject` with `PLATYPUS_STORE_GUARD=reject` or `PLATYPUS_DEBUG=1`, and `npm test` sets it.
  - **`requireFields`**: a store opened with it refuses a collection declared without fields. The engine will open its store this way (S9); the conformance suite does not, because most of its collections are free-form on purpose.
  - **Paths.** `relPath(file, root)` gives the path relative to the project root, with forward slashes. Anything outside the root, or absolute without a known root, becomes `ext:<10 hex of the sha1 of the full path>/<file name>`. A field of type `path` can never hold an absolute path: the guard converts it.
  - **Excerpts.** `scrub(text)` replaces with a placeholder: tokens with a known prefix (GitHub, GitLab, Anthropic, OpenAI, AWS, Google, Slack, Stripe, npm, Hugging Face), JWTs, `Bearer`/`Basic` headers, `name=value` and `--name value` where the name is a secret word, credentials inside URLs and connection strings, PEM private keys, e-mail addresses, IBANs with a valid check digit, and long mixed-case sequences. `excerpt(text)` makes one line, scrubs, then cuts at 200 characters. A field of type `excerpt` always goes through it.
  - No filter existed in the code to reuse (searched `src/` for scrub, redact, secret, password): this is the first.

  - Conformance suite: 59 ok on `memory` and 59 on `sqlite` (7 new: a valid document passes untouched, 15 kinds of bad field refused in put, append and patch, the drop mode, the one-time report without values, paths and excerpts, bad declarations, `requireFields`).

- Decisions:
  - **A free string is limited to one line and 300 characters.** That is what keeps a prompt or a reply out even when a field is declared: text does not fit. Longer or multi-line values are refused or dropped, not cut, since half a text is still text.
  - **The file name of a path outside the project is kept**, as the task says ("a hash with the file name alone"). A file name can itself say something (`conti-2026.xlsx`); the folder cannot be seen.
