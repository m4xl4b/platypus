# Platypus 2.11 → 3.0 — Feedback to the agents · Storage · Server mode

Development plan to carry out step by step, one task at a time. It lives in the repository at `docs/plans/2.11-3.0-feedback-storage-server.md`.
Each task has a checkbox: `[ ]` to do, `[~]` in progress, `[x]` done, `[!]` blocked (with the reason below it).
At the bottom is the **Journal**, where whoever works on the plan records, at every step, what they did, what they verified and the decisions they made. The Journal is written in English.

## The idea in one line

Platypus already knows when an agent is about to repeat a known mistake, says "the tests pass" without having run them, or goes round in circles. Today only you see it, in the office. This version lets Platypus **tell the agent**, through Claude Code hooks: rarely, only when you turn it on, and measuring whether it helped.

There are three parts:

1. **The channel:** a hook endpoint that answers Claude Code in a few milliseconds, installed separately from the observing hooks, with a "shadow" mode that only records what it would have said.
2. **What Platypus says:** the project's lessons at session start, Grandpa's lesson before a known trap, a nudge out of a loop, and a check on claims without evidence before the agent stops.
3. **Seeing it and measuring it:** every message to an agent is visible in the office and in the Book, with what happened next.

## The roadmap, in three versions

Discussed with Max on 2026-11-01. Each version is useful on its own and prepares the next one:

| Version | Parts | What it gives |
|---|---|---|
| **2.11** | A–D · Feedback to the agents | Platypus tells the agent what it already sees, opt-in and measured. Stores its log in a small JSONL file, behind a thin interface. |
| **2.12** | E · Storage | A `store` interface with an embedded document store (SQLite built into Node, no npm dependency) on the desktop, and a NoSQL backend (MongoDB) for the server. Long history: trends over months and the effect of the feedback over weeks. |
| **3.0** | F · Server mode in a container | The engine alone in a container, with authentication, fed by several machines: Claude Code in devcontainers, on remote machines or in CI, and a team view with shared project books. |

Later, in a plan of its own: a **Platypus MCP server** that agents can query ("who touched this file?", "does this command usually fail?", "how was this error fixed last time?"), which builds on the storage of 2.12.

Why this order: the feedback is where Platypus becomes useful to the agents and not only to the person watching, and it needs nothing new underneath. The storage then makes the feedback measurable over time. The server mode comes last because it adds the largest risk (data leaving the developer's machine, a network-facing service) and benefits from both.

## Project rules, to follow in every task

All the rules of the 2.9 plan still apply: engine without npm dependencies, strings through `tr`/`trn` with Italian keys and the English translation in `src/i18n/locales/en/` (a new `feedback.json` for this version), cross-platform, everything local, analyses inside `try/catch`, honesty in the interface, a demo scenario for every feature, `npm test` green after every task, one commit per task in English, **never push** unless the user asks. Checks always run on a temporary home, never on real sessions.

Parts E and F relax two of those rules, only where they say so and never for the desktop app: the MongoDB driver is an npm dependency, so it lives outside `src/core` in a separate `server/` package that only the container installs; and in server mode data leaves the developer's machine, so it does so only with explicit consent per machine and per project (E4, F3).

On top of those, for anything that reaches an agent:

- **Off by default, opt-in per feature.** Each feature has three modes: `off`, `shadow` (computes and records what it would say, shows it in the office, sends nothing) and `on`. The defaults are `off`; the options suggest starting in `shadow`.
- **Installed only with consent.** The feedback hooks are separate from the observing ones, installed and removed with their own button and their own confirmation dialog, which shows the exact lines written to `settings.json`. A backup of the file is kept as today.
- **Fail-open, always.** If Platypus is closed, slow, or something throws, Claude Code goes on exactly as without Platypus: a short hook timeout, never `onFailure: "block"`, an empty answer on any error, a time budget on the server side.
- **Never decide for the user.** No tool call is denied, rewritten or approved (no `permissionDecision`, `updatedInput` or `updatedToolOutput`); Platypus only adds context. The single exception is the Stop check (B5), which can ask the agent to continue once per turn, and has its own switch.
- **Say who is talking and why.** Every message starts with "Platypus" and the source of the lesson (dates, number of cases), and says it is inferred from past sessions, not a rule.
- **Rare.** Global and per-feature rate limits (see A3). A message that would repeat itself is not sent.
- **Measured.** Every message, sent or shadowed, is logged with what happened next (C2). A feature that does not help in shadow data does not get turned on by default.

## A. The channel

### A1 · Feedback endpoint  [ ]

- **New route** `POST /platypus-hook/feedback`, synchronous. It reads the hook input (`hook_event_name`, `session_id`, `agent_id`, `cwd`, `tool_name`, `tool_input`, `transcript_path`, `stop_hook_active`…) and answers with the JSON Claude Code expects for that event (see "Hook formats" below), or with an empty `204` when there is nothing to say.
- **Time budget:** the answer is computed in at most 300 ms; past that, `204`. No disk scan on this path: only the in-memory state, the books already loaded, and a stat of the files involved.
- **Fresh state for Stop:** before judging a turn, read the new lines of that session's transcript (`TranscriptWatcher`), so the last tool calls are not missed because of the polling interval.
- **Same-origin rules as the other hook routes:** no `Origin` header (curl), loopback only.
- **New module** `src/core/feedback.js` holds the decisions (pure functions: input + state + lessons → message or nothing), so they can be tested without a server.
- **Tests:** each event with and without something to say; malformed input; an exception inside a rule gives `204`; the budget.
- **Spike first, on a temporary `CLAUDE_CONFIG_DIR`:** with the Claude Code version installed here, confirm (1) that an `http` hook reaches the endpoint and its answer is applied, (2) whether `additionalContext` on `PreToolUse` reaches the model (not confirmed by the docs, see "Hook formats"), (3) that a closed Platypus leaves Claude Code unaffected. Record the version and the results in the Journal; B2–B4 use `PreToolUse` only if (2) holds.

### A2 · Feedback hooks, installed apart  [ ]

- **`hooks.installFeedback({port})` / `uninstallFeedback` / `feedbackStatus`**, with a different marker (`/platypus-hook/feedback`) so that the observing hooks and the feedback hooks can be installed and removed independently.
- **Events and matchers:** `SessionStart`; `PostToolUse` on `Bash|Read|Glob|Grep|Edit|Write|MultiEdit` (and `PreToolUse` on the same tools only if the A1 spike confirms its context reaches the model); `Stop` and `SubagentStop`. Synchronous (not `async`), `timeout` of 3 seconds.
- **Hook type:** `"type": "http"` with `url: http://127.0.0.1:<port>/platypus-hook/feedback`. Claude Code posts the input itself, an empty `2xx` means "nothing to say", and a connection error is non-blocking by default (never set `onFailure: "block"`). No `curl`, so nothing depends on the shell. If the installed Claude Code is too old for `http` hooks, fall back to the `curl` command used by the observing hooks.
- **Options panel:** a new group "FEEDBACK TO THE AGENTS" with the three-mode switch for each feature (A3) and the install/remove button with the confirmation dialog showing the lines that will be written.
- **CLI:** `npm run hooks:install -- --feedback` and the matching uninstall/status.
- **Tests:** install, remove and status on a temporary `settings.json`; the observing hooks stay untouched byte for byte; installing twice does not duplicate.

### A3 · Modes, limits and the log  [ ]

- **Settings** (all `off` by default): `fbSessionLessons`, `fbElder`, `fbLoop`, `fbClaims`, `fbDrift`, each `off | shadow | on`; `fbLang` (`en` by default, since the reader is the model; `ui` to follow the interface language).
- **Limits:**
  - at most one message per agent every 2 minutes, and at most 6 per session per hour, all features together;
  - the same lesson at most once per agent per session;
  - the Stop check at most once per turn, and never when `stop_hook_active` is true.
- **Per project:** the Book gets a "don't talk to agents in this project" switch.
- **Log:** `~/.platypus/feedback/<project key>.jsonl`, one line per message: `{t, sid, agent, feature, mode, event, lessonId?, text, outcome?}`, append-only, rotated at 5 MB. Written through a tiny `feedbackLog` interface (`append`, `recent`, `setOutcome`) so the storage plan can replace it.
- **Tests:** limits, the per-project switch, rotation.

## B. What Platypus says

Each feature is a pure rule in `src/core/feedback.js` and a mode in A3. Texts are short (at most 400 characters), start with "Platypus", and cite where the lesson comes from.

### B1 · Lessons at session start  [ ]

- **Event:** `SessionStart` (sources `startup`, `resume`, `clear` and `fork`; also `compact`, since compaction may have dropped what the agent knew). Answer with `hookSpecificOutput.additionalContext`.
- **Content:** the pinned and strongest lessons of the project, the same text as the CLAUDE.md section (`renderSection`), at most 6.
- **Not twice:** if the project's `CLAUDE.md` already has the Platypus section, send nothing.
- **Tests:** a project with lessons, one without, one with the CLAUDE.md section.

### B2 · Grandpa talks to the agent  [ ]

- **Event:** `PostToolUse`, with `hookSpecificOutput.additionalContext` (it reaches the model next to the tool result). The match uses the hook's own `tool_input` and `tool_response`, not the state, so it is exact even if the transcript has not been read yet. Speaking after the tool is also the right moment, and it keeps messages rare: the lesson is sent only when it applies.
  - `Bash` that **failed**, with a `flaky-command` lesson ("rerun it once before investigating") or a `loop-trap` one (via `sameCmd`);
  - `Bash` that took longer than a few minutes, with a `slow-step` lesson ("next time run it in the background");
  - `Read`/`Glob`/`Grep` that found nothing, on a known `ghost-path` ("it was probably renamed: …");
  - `Edit`/`Write` on a `fragile-file` ("run the tests after changing it");
  - a failure whose error pattern matches a `known-fix` ("last time it was fixed in `file`").
- **Before the tool, only if the A1 spike allows it:** the same lessons for `slow-step` (to suggest running in the background) are more useful before the command, through `PreToolUse`.
- **Text:** the same lesson as Grandpa's balloon (`elderLine`), addressed to the agent.
- **In the office:** when Grandpa's lesson has also been sent to the agent, his balloon says so ("told CLAUDE").
- **Tests:** the four kinds, an ignored lesson, an observation (not sent).

### B3 · Out of the loop  [ ]

- **When:** a command fails for the second time in a row with the same error pattern and no edit in between (the "insists" reaction of the seismograph). The message comes with the second failure, before the third attempt.
- **Text:** "Platypus: this command failed N times in a row with the same error («…») and nothing changed in between. Change something before running it again, or stop and say what is blocking you."
- **Event:** `PostToolUse` on `Bash`, using the live state for the previous attempts and `tool_input`/`tool_response` for the current one.
- **Tests:** two identical failures (sent); a failure, an edit, a failure (not sent); different errors (not sent).

### B4 · Stale memory before an edit  [ ]

- **When:** `PreToolUse` on `Edit`/`Write` of a file this agent read, that changed afterwards (another agent or outside the session). Needs the A1 spike to confirm `PreToolUse` context; otherwise `PostToolUse` after a `Write` that overwrote someone else's change ("check you did not undo …'s change").
- **Check first in shadow:** Claude Code already refuses an edit to a file modified since it was read (Platypus counts those as "stopped" blind edits). This feature stays `shadow` until the data shows cases that Claude Code does not catch, for example a `Write` over a file read long ago, or changes made by another agent through `Bash`.
- **Tests:** a file changed by another agent; one changed by the same agent (not sent).

### B5 · Claims without evidence before stopping  [ ]

- **Event:** `Stop` (and `SubagentStop` for subagents).
- **Input:** the claims come from `last_assistant_message` (the transcript may not hold the final reply yet at Stop time); the evidence from the turn's tool calls in the state, after reading the transcript's new lines (A1).
- **When:** the last turn contains a claim of kind `tests` or `verified` ("the tests pass", "I verified…") that `checkClaims` judges **ungrounded** (no test or check run in the same turn) or **contradicted** (the last outcome is a failure).
- **What it does:** returns `decision: "block"` with a reason such as "Platypus: you said «the tests pass», but no test ran in this turn (last run: failed at 17:42). Run them, or say that it is not verified." The agent continues once; `stop_hook_active` prevents a second block.
- **Only these two kinds:** "fixed" and "done" are not checked here, since their evidence is less reliable.
- **Tests:** an ungrounded claim (block), a grounded one (nothing), a contradicted one (block), `stop_hook_active` (nothing), a turn without claims (nothing).

### B6 · Back to the task  [ ]

- **Experimental, shadow only in this version.** When the north star shows drift (alignment under 0.35 for 6 actions in a row, the same rule as the map), a `PostToolUse` context reminds the agent of the original task, quoted.
- **Why shadow only:** the lexical engine can't tell a necessary detour from a drift; the data in C2 decides whether it is ever turned on.

## C. Seeing it and measuring it

### C1 · In the office and in the Book  [ ]

- **Office:** a small "Platypus said…" balloon on the agent that received a message, with the text on hover; a different mark for shadow messages ("would have said").
- **Book:** a "FEEDBACK" tab for the project with the log: when, to whom, which feature, sent or shadowed, the text and the outcome.
- **Options:** the counts of the last 7 days next to each feature's switch.

### C2 · Outcomes  [ ]

- **For each message, what happened next,** computed from the facts already tracked, with honest labels ("likely helped", "ignored", "can't tell"):
  - B2 and B3: the next run of that command succeeded, or the agent changed something before retrying, versus the same failure again;
  - B5: a test or check ran before the end of the turn, or the agent withdrew the claim, versus nothing;
  - B1: the session avoided the lessons' traps, compared with sessions of the same project without the message.
- **Shadow messages get the same outcome,** which is the baseline: what agents do when nobody tells them.
- **Tests:** outcome rules on synthetic sessions.

### C3 · Demo and tests  [ ]

- **Demo:** one scenario per feature on the demo floors, with simulated hook calls, so every balloon and the FEEDBACK tab are visible within a few minutes of demo.
- **End-to-end test:** `smoke-test.js` posts hook inputs to the running server and checks the JSON answers.

## E. Storage (2.12)

Today Platypus keeps a few JSON files in `~/.platypus` (settings, stats, one book per project; about 300 KB on Max's machine) and rebuilds everything else from the transcripts. That is enough for the office, not for questions over months ("is this project getting more loops?", "did the Stop check reduce unverified claims since October?") nor for several machines writing at once.

### E1 · The `store` interface  [ ]

- **New module** `src/core/store/index.js`: a small document API used by the whole engine instead of direct file access.
  - `get(coll, id)`, `put(coll, doc)`, `update(coll, id, patch)`, `remove(coll, id)`;
  - `find(coll, filter, {sort, limit})` with a deliberately small filter language (equality, ranges on numbers and dates, `in`), so every backend can implement it;
  - `append(coll, doc)` for logs, with `retentionDays` per collection.
- **Collections:**

| Collection | Content | Today |
|---|---|---|
| `lessons` | the Workshop book, one document per lesson, with the project key | `~/.platypus/bottega/<key>.json` |
| `feedback` | the 2.11 messages and their outcomes | `~/.platypus/feedback/*.jsonl` |
| `stats` | daily counters (cost, tokens, errors, tasks) | `stats.json` |
| `steps` | per-session step metadata: time, action, target, outcome, phase. **No transcript text** | not stored, rebuilt from transcripts |
| `sessions` | one summary per session: project, duration, cost, agents, workflows | the archive list, rebuilt |

- **Backend chosen** by `settings.store` or `PLATYPUS_STORE` (`json`, `sqlite`, `mongo`). Default `json` in 2.12.0, `sqlite` once E2 has run on Max's machine for a while.
- **Tests:** the same suite runs against every backend (a shared contract test).

### E2 · Embedded document store: SQLite built into Node  [ ]

- **`node:sqlite`** (in Node since 22.5, without a flag from 22.13; Electron 44 ships Node 24.22, where it was checked on 2026-11-01). No npm dependency and no native module to rebuild for Electron.
- **Document model on SQLite:** one table per collection with `id`, a few indexed columns (project, time, kind) and the document as JSON; filters on other fields use `json_extract`. It behaves like an embedded NoSQL store, with transactions and one file (`~/.platypus/platypus.db`, WAL mode).
- **Migration:** at first start with `sqlite`, import the JSON files, keep them as a backup, write a marker; a failed import leaves the `json` backend in place.
- **Minimum Node:** raise the window's requirement from 22.12 to 22.13 in `scripts/requirements.js`; without `node:sqlite`, fall back to `json` with a notice.
- **Tests:** the contract test; migration from a copy of the JSON fixtures; a corrupted file falls back to `json`.

### E3 · NoSQL backend for the server: MongoDB  [ ]

- **Why a document database there:** lessons, feedback, steps and session summaries are already documents; MongoDB adds TTL indexes for retention, aggregations for trends, and change streams so that several Platypus instances behind the same database see each other's updates live.
- **Where the code lives:** `server/store-mongo.js` in a separate `server/` package with its own `package.json` (the official `mongodb` driver, pinned). `src/core` loads it only when `store` is `mongo`, so the desktop app stays without dependencies.
- **Indexes:** `{project, kind}` on `lessons`; `{project, t}` on `feedback`, `steps`, `sessions`; TTL on `steps` and `feedback` from `retentionDays`.
- **Tests:** the contract test against a MongoDB started by the CI job (service container), skipped locally when none is available.

### E4 · What is stored, and privacy  [ ]

- **Derived facts only, by default:** times, actions, targets (paths relative to the project), outcomes, lesson keys, short error patterns already normalized by `errorPattern`. Never prompts, replies, file contents or command output.
- **Excerpts** (the one-line evidence shown in the Book) only if `storeExcerpts` is on, after a secret scrubber (tokens, keys, passwords, connection strings).
- **Retention:** `retentionDays` per collection (defaults: steps 90, feedback 180, lessons kept while their weight is above the observation threshold).
- **Deleting:** "Forget this project" removes its documents from every collection; the INSTALL guides say where the database lives and how to delete it.

### E5 · Long history in the interface  [ ]

- **Trends per project** in the Book: loops, unverified claims, flaky commands and cost per week.
- **The effect of the feedback over time** (C2 over weeks): sent versus shadow, per feature.
- **Archive search** on the stored step metadata (by file, command or error pattern), much faster than replaying transcripts.

### E6 · Docs, version and check  [ ]

- ARCHITECTURE (EN/IT), INSTALL (EN/IT), CHANGELOG (EN/IT), version 2.12.0.
- A week on Max's machine with `sqlite`, then the default switches from `json` to `sqlite`.

### NoSQL options considered

| Option | Fits | Doesn't fit | Verdict |
|---|---|---|---|
| **SQLite with JSON documents** (`node:sqlite`) | desktop: zero dependencies, one file, transactions, JSON queries | many writers on a network | **embedded backend** |
| **MongoDB** | server: documents as they are, TTL, aggregations, change streams, mature driver and hosting (self-hosted or Atlas) | the desktop (a server to run, an npm driver) | **server backend** |
| **CouchDB / PouchDB** | replication between machines, offline-first: each developer keeps a local book and syncs it with the team without a central Platypus | heavier to query for trends; PouchDB is an npm dependency | **to evaluate** if the team prefers sync to a central server |
| **Redis** | live state and pub/sub between instances | primary storage (memory-bound, persistence is secondary) | maybe later, next to MongoDB, for many instances |
| **LevelDB / LMDB** | fast embedded key-value | native modules to rebuild for Electron; no queries | no |
| **Elasticsearch / OpenSearch** | full-text search over large archives | weight and operations for what Platypus needs | no, unless transcript text search becomes a goal |
| **DynamoDB / Firestore** | managed, scales | ties Platypus to one cloud and sends data off-site by design | no |

## F. Server mode in a container (3.0)

Today the engine listens only on `127.0.0.1`, reads `~/.claude` from the local disk, and trusts every local caller. Server mode keeps the same engine and office, and changes three things: where the events come from, who may connect, and where the data is stored.

### F1 · Headless image  [ ]

- **`Dockerfile`** for the engine alone (`src/standalone.js --no-open`, no Electron): a `node:24-slim` base pinned by digest, a non-root user, a read-only root filesystem with one writable volume for data, `HEALTHCHECK` on a new `GET /api/health`.
- **Configuration through environment variables:** `PLATYPUS_PORT`, `PLATYPUS_BIND` (default `127.0.0.1`; anything else requires F2), `PLATYPUS_STORE`, `PLATYPUS_MONGO_URL`, `PLATYPUS_CLAUDE_DIRS` (already supported), `PLATYPUS_TOKEN_FILE`.
- **Image size and supply chain:** only `src/`, `renderer/` and `server/`; `npm ci --omit=dev` in `server/`; image scan in CI; a published SBOM.

### F2 · Authentication and transport  [ ]

- **No anonymous access outside loopback:** the server refuses to start bound to a non-loopback address without a token.
- **Tokens:** an admin token from a file or secret; per-machine tokens for ingestion (F3), revocable; the office UI signs in with a token and gets an `HttpOnly`, `SameSite=Strict` cookie.
- **TLS** through a reverse proxy in the compose file (Caddy, automatic certificates on a real domain, internal CA on a LAN).
- **The existing guards stay:** CSP, `Origin` checks, no iframes. **Approving permissions from the office** (the synchronous PermissionRequest hook) is off in server mode unless it is explicitly turned on per machine: a network service must not be able to approve commands on a developer's machine by default.
- **Tests:** refused without a token; a revoked token; the cookie; approvals off by default.

### F3 · Where the events come from  [ ]

Three sources, which can be mixed:

1. **A mounted `~/.claude` (read-only),** when Claude Code runs on the same host or in a devcontainer next to Platypus: the current watcher, unchanged.
2. **Hooks from each machine:** the observing hooks become `http` hooks pointed at the server, with the machine token in a header (`headers` + `allowedEnvVars`, so the token is not written in `settings.json`). Live, but only what hooks carry.
3. **A small forwarder** (`platypus forward`, part of the desktop app and of the CLI) that reads the local transcripts and sends **derived steps**, not text, to the server: the same facts as E4. It covers what hooks don't (outcomes, replies judged for claims) and works offline, with a queue.

- **Consent:** forwarding is off until the developer turns it on, per project, from the desktop app, which shows the server address and what will be sent.
- **Paths:** a mapping from each machine's project folders to a project identity (F4), so the server never needs the developer's absolute paths. Disk checks (grounding) run on the developer's machine, in the forwarder, and only their results are sent.

### F4 · Team view  [ ]

- **Project identity across machines:** the project key becomes the normalized `git remote` URL when there is one (folder path otherwise), so the same repository on three laptops shares one Workshop book.
- **Lobby:** floors per project with the machines and people active on it; the office shows whose agent is whose.
- **Shared books:** lessons learned on any machine help everyone; the Book shows on which machine each case happened.
- **Feedback in server mode:** the 2.11 endpoint answers remote agents too, with the same fail-open rules and a network-aware time budget; lessons from the shared book reach every developer's agents.

### F5 · Compose file and operations  [ ]

- `docker-compose.yml` with `platypus`, `mongo` (with a volume and authentication) and `caddy`; a `.env.example`.
- Backups (`mongodump` on a schedule), upgrades (schema version in the database, migrations on start), logs to stdout.
- A guide, `docs/SERVER.md` and `docs/SERVER.it.md`: one-machine devcontainer setup, team setup, how to connect a laptop, how to delete a machine's data.

### F6 · Security review and final check  [ ]

- **Threat model:** stolen machine token (scope: ingestion only, revocable), exposed office (token, TLS), remote approvals (off by default), data at rest (MongoDB auth, volume encryption left to the host), excerpts with secrets (E4 scrubber).
- **Check:** compose up on a clean machine; two "machines" (two temporary homes) forwarding to it; the team view; the feedback reaching an agent through the server; Platypus closed or the server down leaves Claude Code unaffected.
- CHANGELOG (EN/IT), README (EN/IT), version 3.0.0.

## Hook formats

From the Claude Code hooks reference (code.claude.com/docs/en/hooks), read on 2026-11-01 through a summarizing fetch: check exact strings against the page, and against the installed version in the A1 spike.

| Event | What Platypus returns | Notes |
|---|---|---|
| `SessionStart` | `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "…"}}` | `source`: `startup`, `resume`, `clear`, `compact`, `fork`. Cannot block. |
| `PostToolUse` | `{"hookSpecificOutput": {"hookEventName": "PostToolUse", "additionalContext": "…"}}` | Added next to the tool result; the tool already ran. Never use `decision: "block"` or `updatedToolOutput`. |
| `PreToolUse` | `hookSpecificOutput.additionalContext`, **not confirmed** | Never return `permissionDecision` or `updatedInput`: with no decision, the normal permission flow goes on. |
| `Stop` / `SubagentStop` | `{"decision": "block", "reason": "…"}` | `reason` is required and is what the agent reads. Input has `stop_hook_active` and `last_assistant_message`; Claude Code also stops honouring blocks after 8 in a row. |
| any | empty `2xx` | Nothing to say. |

Failure behaviour: an `http` hook with a connection error, a non-`2xx` answer or a timeout is a non-blocking error (the action goes on) unless `onFailure: "block"`, which Platypus never sets. Hooks also run inside subagents, with `agent_id` and `agent_type` in the input.

Also noted, for later: an `async` command hook can return `additionalContext`, delivered to the model on the next turn. It could carry low-priority lessons without making any hook synchronous.
